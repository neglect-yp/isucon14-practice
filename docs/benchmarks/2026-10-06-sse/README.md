### 通知の読み方

変更前の通知 HTTP は利用者 49,445 件・椅子 45,394 件、合計 **94,839 件**。最終版で集計区間に重なる SSE 接続は利用者 **1,531 本**・椅子 **293 本**、合計 **1,824 本**。全接続が HTTP 200、User-Agent は `isucandar`。[接続数](./sse-summary.json)

前者は区間内に完了したポーリング、後者は区間に重なる長時間接続なので、同じ意味のリクエスト件数ではない。各 SSE 接続で複数の通知を配信する。接続数は元 nginx ログの `content_type=text/event-stream`、`完了時刻 >= 区間開始`、`完了時刻 - response_time < 区間終了` で抽出した。

最終 alp の利用者通知は 1,324 件、平均 6.798 秒、p95 14.490 秒だが、これは **接続継続時間**。通知の遅延ではない。椅子の SSE は区間内に接続終了しなかったため alp に載らない。今回は個々の状態変更から配信までの遅延分布は計測しておらず、仕様の検証は変更していないベンチマーカーの PASS で確認した。

## slp: 距離集計と残る負荷

owner/chairs の距離 SQL は、N+1 解消後の **平均 300.596 ms → 絞り込み後 49.087 ms**、累積 **42.384 → 7.167 秒**。SSE で処理量が増えた最終版では平均 **89.569 ms**、累積 **13.883 秒**だった。変更前の平均 331.969 ms・累積 51.123 秒より小さい。

最終版の主な SQL:

| SQL | 回数 | 累積秒 | 平均 ms |
| --- | ---: | ---: | ---: |
| COMMIT | 116,371 | 359.410 | 3.088 |
| 利用者通知の送信済み UPDATE | 8,347 | 54.232 | 6.497 |
| 椅子通知の送信済み UPDATE | 8,535 | 43.885 | 5.142 |
| 最新状態の SELECT | 462,513 | 29.726 | 0.064 |

| 椅子の評価集計 | 20,833 | 9.979 | 0.479 |

COMMIT は SQL 累積時間の約 60.7%。SSE では送信済みの更新を autocommit の UPDATE に分離したため、その書き込み確定の待ちは UPDATE 時間に含まれる。COMMIT だけを前後比較して通知の書き込み待ちが解消したとは判断しない。

最終版の SQL 総回数は変更前とほぼ同じで、総時間は 472.535 → 591.816 秒、総走査行数は 4,744,933 → 7,629,262 と増えている。その間、位置更新やライド作成の処理量も増えた。SSE 追加直前との比較では SQL 総時間は 694.424 → 591.816 秒に減った。

## COMMIT 待ちの調査

変更前の slow log を MySQL `Thread_id` ごとの `BEGIN` から `COMMIT` までに分け、SQL の特徴で分類した。[分類結果](./baseline-transaction-breakdown.json)

| トランザクション | COMMIT 回数 | COMMIT 累積秒 |
| --- | ---: | ---: |
| 位置更新 | 32,795 | 196.162 |
| 送信済み更新のある通知 | 10,475 | 67.987 |
| 読み取りのみの通知 | 82,179 | 2.126 |

位置更新が全 COMMIT 時間の **67.1%**。読み取りだけの通知は回数こそ多いが、COMMIT の大半ではない。区間境界で開始を確認できない 3 件は未分類とした。

最終版では Performance Schema のファイル I/O カウンターもベンチマーク実行前後で取得した。以下は **初期化・検証を含む全実行区間** の差分で、57.6 秒の alp / slp とは区間が異なる。[全差分 CSV](./file-io-delta.csv)

| ファイル種別 | read 回数 / 秒 | write 回数 / 秒 | misc 回数 / 秒 |
| --- | ---: | ---: | ---: |
| InnoDB data | 1 / 0.000198 | 33,470 / 0.433 | 2,074 / 1.527 |
| InnoDB redo log | 0 / 0 | 83,506 / 3.986 | 45,673 / 26.478 |
| binlog | 0 / 0 | 28,761 / 2.299 | 24,894 / 34.632 |
| slow log | 0 / 0 | 1,697,472 / 11.294 | 0 / 0 |

読み込み I/O よりログの書き込み・同期周辺を優先して調べる根拠になる。ただし `MISC` は fsync 以外の操作も含み、特定の座標更新と紐付いていないため、**redo / binlog の同期が COMMIT 待ちに寄与するという仮説**まで。並列 COMMIT の累積秒とファイル I/O の累積秒を直接引き算することもできない。[MySQL 公式資料](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-file-summary-tables.html)

`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`、`log_bin=ON` を維持。耐久性設定の緩和や binlog の無効化は行っていない。slow log 自体にも書き込み時間があり、このスコアは全 SQL 記録を有効にした条件の結果。

## 変更内容

根拠はこの練習のログとソース、[通知の仕様](../../ISURIDE.md#通知エンドポイント)。問題の解説や他者の実装は参照していない。

### SQL

- [app_handlers.rs](../../../webapp/rust/src/app_handlers.rs): 評価集計で全 ride を取得し、各 ride の状態を別々に取得する処理を、`COUNT` / `SUM` / `EXISTS` にまとめた。CARRYING・ARRIVED・COMPLETED がすべて存在する条件は維持し、同じ状態の重複で ride 数が増えないようにした。
- [owner_handlers.rs](../../../webapp/rust/src/owner_handlers.rs): LAG / SUM の前にオーナーの椅子で座標履歴を絞る。同一スナップショットで旧・新 SQL を比較し、100 椅子、52 椅子、0 椅子の各対象で結果一致を確認した。距離の計算式と反映時点は維持。

### SSE

[notifications.rs](../../../webapp/rust/src/notifications.rs) に利用者・椅子の共通処理を実装した。

- 状態履歴と送信済み情報は MySQL に保持。プロセス内には宛先別の起床通知だけを持つ。
- ライド作成・配車・状態更新・評価の **commit 後** に該当接続を起こす。購読登録を最初の DB 読み取りより前に行う。
- 起床通知が複数回分まとめられても、DB の履歴を順に読み、ライドをまたぐ未送信状態も順序どおり送る。
- 再接続は未送信履歴、なければ最新状態を返す。`Last-Event-ID` があれば、その宛先に属する状態 ID の後から再送できる。他の利用者の ID は利用できない。
- レスポンス body にイベントを渡した後、次の body poll で送信済みを記録する。これはクライアントの受信 ACK ではない。`Last-Event-ID` により再送できるが、ヘッダーなしの再接続でネットワーク断直前の受信を完全に判定する仕組みではない。
- 待機中は DB 接続・トランザクションを保持しない。通知取りこぼしや別プロセスからの書き込みに備えて 1 秒ごとにも再確認するため、待機中の SQL はゼロではない。プロセスをまたぐ即時配信が必要なら通知経路の共有が別途必要。
- 10 秒ごとの keepalive と `X-Accel-Buffering: no` を返す。nginx による通知の滞留を避ける指定は [nginx 公式仕様](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_buffering) に従う。
- `/api/initialize` は購読を閉じてから DB を初期化する。

## 次の改善候補

1. **周辺の椅子検索の N+1**。[app_handlers.rs](../../../webapp/rust/src/app_handlers.rs) は全椅子を読み、稼働椅子ごとに全 ride と状態を確認する。椅子別 ride 取得だけで 273,558 回、HTTP 平均 343 ms・p95 996 ms。対象と状態をまとめて取得する候補で、未検証。
2. **位置更新・通知済み記録の書き込み待ち**。前述の COMMIT 分類とログ I/O が根拠。まず最新位置の参照と座標履歴の保存をどう分担するか、必要な記録と同期回数を仕様に照らして検討する。現時点で原因の完全な切り分けや追加変更はしていない。
3. **処理量増加後の配車待ち**。最終不満率は、配車待ち 18.4% → 56.4%、迎車 30.7% → 37.2%、実移動 82.0% → 67.4%。総スコアは伸びたが配車待ちは悪化した。待機ライド数、空き椅子数、距離の分布を次に計測し、配車頻度・選択方法と単純な供給不足を切り分ける。
