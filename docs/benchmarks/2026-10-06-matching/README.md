## 調査と変更

根拠はこのリポジトリのソース・仕様書と、[前回の計測](../2026-10-06-indexes/README.md)。問題の解説や他者の解答は参照していない。

### 配車をまとめ、迎車時間を考慮する

旧 [internal_handlers.rs](../../../webapp/rust/src/internal_handlers.rs) は呼び出しごとに 1 ライドを選び、ランダムに椅子を探していた。前回の集計区間では新規ライド API が 175 件、matching 呼び出しが 110 件、椅子割り当て UPDATE が 109 回。呼び出し後に 0.5 秒待つ構成なので、1 件ずつでは毎秒 2 件未満に制限される。

- 待機ライドを古い順に最大 64 件まで配車する。
- 空いている椅子の最新座標・モデル速度をまとめて読み、マンハッタン距離 / 速度が小さい椅子を選ぶ。選択済みの椅子は候補から除く。全体最適化ではなく、各ライドに対する貪欲な選択。
- 配車トランザクションの最初に椅子を `FOR UPDATE SKIP LOCKED` でロックし、その後に空き状態を読む。同時に呼ばれても同じ椅子を使い回さないようにした。
- 元の「過去の全ライドで 6 状態すべてを椅子へ通知済み」という条件を維持。完了未通知・利用中・非稼働・座標未取得の椅子は対象外。
- ライドもロックしてから割り当て、プロセス内に配車状態を保持しない。

[ISURIDE.md](../../ISURIDE.md) の速度・距離と配車条件、[競技マニュアル](../../manual.md) の完了通知条件を参照した。MySQL のスナップショットをロック後に作る理由は、[公式の locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html) と [transaction isolation levels](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html) で確認した。

### 全件走査と広いロック範囲を減らす

[1-schema.sql](../../../webapp/sql/1-schema.sql) に以下 8 本を追加。前回の 2 本も維持する。

| テーブル | インデックス列 | 対象 |
| --- | --- | --- |
| chairs | access_token | 毎回の椅子認証 |
| chairs | is_active | 配車候補のロック |
| rides | user_id, created_at | 利用者の最新ライド |
| rides | chair_id, updated_at | 椅子の最新ライド |
| rides | chair_id, created_at | 未配車ライドの順序付き検索・椅子の履歴 |
| coupons | used_by | ライドに使用したクーポン |
| coupons | code | 招待回数の確認 |
| coupons | user_id, used_by, created_at | 利用者の未使用クーポンを古い順に取得・ロック |

最初の 4 種類の頻出検索（利用者・椅子の最新ライド、椅子認証、使用済みクーポン）は前回、合計 SQL 時間の 40.5% を消費し、全件走査していた。変更後の EXPLAIN ではすべて `type=ref` で対応インデックスを利用。クーポン使用・未配車ライドの検索にも対応インデックスが使われ、filesort はない。[確認 SQL](./explain.sql) / [実行計画](./explain.txt)。

### 招待処理のデッドロックを修正する

最初の試行でユーザー登録 4 件、ライド作成 1 件が MySQL 1213 で失敗した。[InnoDB の記録抜粋](./deadlock.txt) では、登録トランザクションがクーポンの 931 行をロックし、利用処理と PRIMARY / used_by インデックスのロック取得が交差していた。

[app_handlers.rs](../../../webapp/rust/src/app_handlers.rs) の登録処理を、招待者の既存ユーザー行を先にロックし、その後で招待数を読む順序に変更した。クーポン全体への `FOR UPDATE` は不要になり、同じ招待コードだけを直列化して上限 3 人を守る。報酬クーポンの識別子は招待先ユーザー ID を末尾に使い、同じミリ秒内でも衝突しないようにした。クーポンの金額・付与順・利用順は維持する。一般的なロック範囲と取得順の扱いは [MySQL 公式資料](https://dev.mysql.com/doc/refman/8.4/en/innodb-deadlocks-handling.html) を参照した。
