# #6: SSE の同一内容の再構築抑制（不採用）

SSE は 1 秒ごとの DB 再確認や通知後の排出処理で、状態が変わっていなくても料金・椅子・統計を取得し直し、JSON を組み立ててから前回と比較していた。状態 ID、椅子 ID、ライド更新時刻、椅子のライドの最新更新時刻を比較し、変化がない場合はペイロード作成を省略する。

DB の再確認自体は 1 秒ごとに続け、別プロセスによる更新や通知の取りこぼしから回復する。配車で椅子が付いた場合や、別ユーザーが同じ椅子を評価した場合も再計算する。名前など API 経由で更新されない登録情報は不変として扱う。

実 HTTP の SSE テストに、別ユーザーの完了ライドによって、現在の状態が PICKUP のまま統計だけ更新されるケースを追加。ローカルの通知を出さず、DB 再確認だけで反映されることを確認する。状態の順序、再接続、利用者分離、接続を保持中の DB 解放も検証する。

検証: Rust の統合テストを含む 13 件が成功。#5 のあとに修正した SSE 切断時のトランザクション問題は、比較元・変更後の両方に含めた。

除外した計測: `20261006-224724` は PASS・136,412 点だが、待機条件の誤りで #7 のビルド・テストが負荷走行中に実行された。スコアによる選別ではなく比較条件違反として除外し、作業が終了してから同じイメージを再計測した。元のログは `_tmp/profiles/20261006-224724` に保存している。

追加比較への切り替え時、次の #7 の起動と比較元の起動が重複したため、`20261006-225220` は中断した。競合した比較元は負荷走行前に終了。重複したアプリコンテナを削除し、MySQL の 7 設定が計測前に戻ったことを確認した。以後は比較スクリプトの Compose 起動も含めて排他制御する。この試行も採否の比較には含めない。

比較元の追加計測 `20261006-225331` には CODE=17 が 1 件あり、アプリログで `users.username` の一意制約違反（MySQL 1062）を確認した。登録処理は今回の変更対象外で、警告を含めた結果を掲載し、除外していない。

## 採否

不採用。3 回ずつの中央値で評価集計 SQL は 36,399 → 14,977 回、累積 44.255 → 16.723 秒に減った。しかし SQL 全体の累積時間は 421.263 → 449.754 秒、COMMIT は 74.409 → 155.739 秒となった。評価 API 件数は 2,393 → 2,297、位置更新件数は 91,707 → 89,316。集計削減を全体の改善へつなげられなかった。

変更後のスコアは 138,513〜177,164 と幅があり、中央値は比較元を下回る。COMMIT の増加を環境の誤差と断定せず、更新頻度・同時実行・DB 待ち時間との関係も未解決として残す。最初の高い 1 回だけで採用せず、元の処理を維持して #7 / #8 を独立して検証する。
