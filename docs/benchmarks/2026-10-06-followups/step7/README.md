# #7: 走行距離の差分集計

オーナーの椅子一覧は、要求のたびに座標履歴を LAG / SUM で走査して総移動距離を求める。直前までの計測では呼び出しは百数十回程度だが、履歴が増えるほど走査量が増える。読み取り時間を削減する一方、頻繁な座標更新に追加書き込みが発生するため、座標 API と全体スコアへの影響も採否に含める。

椅子ごとの直前座標・累積距離・更新時刻を別テーブルに保持し、座標履歴の保存と同じトランザクションで差分を加算する。1 バッチには同じ椅子を複数入れず、履歴を省略しない。オーナー一覧は集計表へ LEFT JOIN する。

初期化は既存データ読み込み後に `4-derived-data.sql` で履歴から集計を復元する。旧・新のイメージには、それぞれの SQL ディレクトリのスナップショットを対応させて比較する。

座標の統合テストで、初期履歴、同じ場所への更新、移動後の値、再集計を繰り返しても二重加算されないことを確認する。座標保存の失敗・初期化前の待機書き込みの拒否を含む既存の整合性検証も実行する。

変更前の #5-safe の計測では距離集計は 160 回・累積約 27〜28 秒、一覧 API は平均約 183〜190 ms。集計の読み取りコストを減らせるが、位置更新は約 9 万回あるため、追加書き込みの影響を確認する仮説とした。

整合性検証では、座標・距離を書き込んだ後の状態履歴 INSERT に故意にエラーを発生させ、履歴と距離の両方がロールバックされることも確認。MySQL で実行した統合テストを含む 13 件が成功した。

#6 は比較で採用しなかったため、比較元と変更後のどちらにも #6 の変更を含めない。

## 採否と整合性

採用。スコア中央値は +1.1% にとどまり、全体スコアへの大きな効果を確認したとはいわない。オーナー一覧は平均 172 / 193 ms → 15 / 15 ms、p95 は 471 / 510 ms → 40 / 52 ms。距離集計 SQL の累積時間は 25.437 / 28.675 秒 → 0.207 / 0.148 秒と、対象の読み取り時間の短縮を 2 回とも確認した。

位置更新は平均 88 / 101 ms → 96 / 99 ms、件数は 91,504 / 89,650 → 90,868 / 88,956。追加書き込みには負担があり、位置更新まで速くなったとはいえない。SQL 全体の累積時間は 421.263 / 407.263 秒 → 361.551 / 430.122 秒で、一律の短縮ではない。

`20261006-230348` の負荷後、全位置履歴から LAG / SUM で距離を再計算し、849 台について保存した総距離・最終更新時刻との不一致は 0 件だった。整合性確認用 SQL は [verify-distance.sql](./verify-distance.sql)。

比較元 2 回と変更後の 2 回目に CODE=17 が各 1 件あり、アプリログはいずれも `users.username` の一意制約違反（1062）。登録処理は変更していない。警告がある回も掲載・比較に含めており、警告なしの性能を保証する結果ではない。
