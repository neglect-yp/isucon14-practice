# #4: 決済中の DB 接続解放と冪等な再試行

評価 API は外部決済の完了まで DB のトランザクションと接続を保持し、決済の再試行時には支払い履歴とユーザーの全ライドを取得していた。直前の計測で評価 API は 1,000 回超、平均約 0.6 秒を占めており、利用完了と次の配車を待たせる時間の短縮を仮説とした。

ライド・支払情報の読み取りを短いトランザクションで終え、DB 接続を解放して決済する。ライド ID を安定した Idempotency-Key として全再試行で共有し、HTTP Client を AppState で再利用する。決済成功後にライドをロックして状態を再確認し、評価・COMPLETED を一度だけ保存する。通知はコミット後に起こす。

根拠はこのリポジトリの `docs/ISURIDE.md` の「Idempotency-Key ヘッダを利用したリクエストの重複防止」と `webapp/payment_mock/openapi.yaml`。外部サービスの仕様やベンチマーカーは変更していない。

DB 接続が 1 本の統合テストで、決済の応答待ち中にも別 SQL が実行できることを確認する。決済済みなのに応答が失敗するケースと並行評価を重ね、同じキーの使用、COMPLETED が 1 件であること、両要求の完了時刻の一致を検証する。

全 11 テストが PASS。ビルドとテストは比較元の負荷走行が終了してから実行し、負荷走行中の CPU を競合させていない。

比較元の `20261006-215911` はスコア 110,157 / PASS だが、`map[17:1]` の警告を伴う。アプリのログではユーザー登録の `users.username` に対する一意制約違反（1062）で HTTP 500 になっていた。この計測を黙って除外せず表に含め、警告なしの計測と区別する。#4 ではユーザー登録処理・制約を変更していない。1 回の警告から発生頻度やスコアへの影響量までは確定できない。

スコア中央値: 比較元 **110,376** → 変更後 **118,069**（+7.0%）。各構成 2 / 2 回で、ばらつきの評価は限定的。

ベンチマーカーは変更なし。全 SQL 記録・60 秒走行・Colima の資源割当・DB の耐久性設定は固定。旧・新の Docker イメージを切り替えて交互に計測した。各集計は既存 tick の最初から最後までで、SSE の HTTP 時間は接続継続時間。SQL 累積秒は並列実行の合計。

実装差分はこのレポートと同じコミット。各計測時の HEAD は実装前のコミットなので、実際の実行物は保存した image ID でも識別する。[実行情報](./runs.json)。生ログは `_tmp/profiles/` に保存し、正規化した集計のみ Git に含める。

採用: 変更後の 2 回は警告なしの PASS で、両スコアが比較元の 2 回を上回った。評価 API の平均は 566 / 611ms → 391 / 391ms、p95 は 1,685 / 1,808ms → 756 / 739ms。件数は 1,522 / 1,539 → 1,602 / 1,717 に増えた。

SQL の累積時間自体は減っておらず、近隣検索の平均も 309 / 336ms → 447 / 506ms に悪化した。決済処理の改善を全体的な DB 負荷削減とは扱わない。処理量の増加と近隣検索の N+1 による影響は次の #5 で切り分ける。HTTP Client の再利用・再試行方式・DB 接続解放はこの候補としてまとめて比較しており、それぞれ単独のスコア寄与は未測定。
