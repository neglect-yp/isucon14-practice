# #2-initial: 配車の起動を早める初期案（不採用）

新規ライド、椅子の稼働開始、椅子への通知済み記録を契機に、プロセス内の単一 worker が配車する。イベントをまとめ、配車処理後に 50ms の間隔を設けて DB の過剰な呼び出しを抑える。500ms の定期再確認と既存 matcher も維持し、イベント取りこぼしを回復する。

待機ライドがない場合は椅子のロックを省略する。FIFO、距離 / 速度による選択、6 状態の通知完了を待つ条件、同時配車のロック順は維持。初期化中は共通の読み書きロックで worker を待機させる。

HTTP の `/internal/matching` は worker を起こして返すため、その応答時間は配車完了時間ではない。配車待ちの不満率、実際の割り当て数、全体スコアで評価する。SQL の走査量・起動頻度増加も比較する。

除外した実行: `20261006-210155` は負荷走行中にホストの SSH ポート転送と Docker ソケット転送が切断。VM 内の Docker は動作していた。接続拒否による FAIL のため比較に含めず、VM を再起動せずに転送と MySQL の計測前 7 設定を復元して再計測した。

不採用。起動を早めるだけでは両実行でスコアが低下し、迎車時間に不満のあるライドも 63.2% / 57.4% に増えた。次の案では待機候補全体の距離を比較する。
