# #3: 通知送信済み更新の一括化

送信済み更新は従来、通知の状態ごと・宛先ごとの autocommit UPDATE だった。#1 の基準実行では app/chair の更新がそれぞれ多数発生しており、小さな書き込みの待ちをまとめる仮説を検証する。

最大 1ms / 128 件のキューで app/chair の ID をまとめ、同じトランザクションで一括 UPDATE する。キューは 1,024 件に制限し、永続化の完了後に次の通知を準備する。ストリームへ前の通知を渡した後に記録する順序、再接続時の再送、初期化前に滞留した更新の無効化を維持する。

DB 統合テストを含む 10 件を実行し PASS。SSE の全 6 状態の順序、再接続、利用者をまたぐ Last-Event-ID の防止、app/chair 双方の送信済み記録を確認した。

比較元は #1（#2 の配車変更は不採用）。SSH 転送障害で中断した実行は除外し、Go SSH クライアントに経路を固定して両構成を再計測した。ベンチマーカー、アプリ・DB の実行場所、CPU・メモリ割当は維持。[環境差と除外した実行](../forwarding/README.md)。

スコア中央値: 比較元 **102,482** → 変更後 **109,410**（+6.8%）。各構成 2 / 2 回で、ばらつきの評価は限定的。

ベンチマーカーは変更なし。全 SQL 記録・60 秒走行・Colima の資源割当・DB の耐久性設定は固定。旧・新の Docker イメージを切り替えて交互に計測した。各集計は既存 tick の最初から最後までで、SSE の HTTP 時間は接続継続時間。SQL 累積秒は並列実行の合計。

実装差分はこのレポートと同じコミット。各計測時の HEAD は実装前のコミットなので、実際の実行物は保存した image ID でも識別する。[実行情報](./runs.json)。生ログは `_tmp/profiles/` に保存し、正規化した集計のみ Git に含める。

採用: 両方の変更後スコアが比較元の 2 回を上回った。送信済み UPDATE は 18,595 / 18,952 回から 4,554 / 4,781 回へ減少。UPDATE だけでなく全 COMMIT を加えた累積時間も約 335 / 268 秒から 46 / 62 秒へ減ったため、待ちが単に UPDATE から COMMIT に移っただけではない。ただし全 COMMIT には他の処理も含まれる。

座標 API は平均 106 / 101ms → 94 / 90ms、処理件数 62,876 / 64,123 → 67,486 / 70,816。評価 API の件数も増加した。一方、近隣検索は平均 288 / 288ms → 329 / 309ms に悪化しており、全 API が速くなったとはしない。増加した負荷と検索処理の影響は #5 で別に検証する。

初回成功実行の再集計では、測定区間より前の通常形式 SQL ログ 19 件を除外した。測定区間内の終了時刻欠損を無視する変更ではない。集計処理の修正は別コミットで、6 テストを実行済み。
