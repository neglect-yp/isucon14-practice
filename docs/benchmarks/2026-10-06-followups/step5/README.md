# #5: 近隣検索の往復削減と走査量抑制

近隣の椅子検索では、全椅子を取得し、稼働椅子ごとに全ライド、各ライドの最新状態、現在座標を別々に取得していた。直前までの計測では、このライド・状態検索が数十万 SQL を占める。通信の往復を減らして近隣検索の応答と DB 接続の占有時間を短縮する仮説を検証する。

最新時刻の GROUP BY / MAX を索引で求め、最新座標を結合して距離で候補を絞る。候補の椅子 ID を一括で渡し、その候補の全ライドを調べて未完了の椅子を除外する。2 回の SELECT で取得し、N+1 は作らない。「過去に一つでも未完了ライドがある椅子を除外」の条件を維持し、最新ライドだけを調べる簡略化は行わない。同じ時刻の場合は ID で順序を確定する。

統合テストでは、稼働・停止、距離の境界、古い座標と最新座標、古い未完了ライドと新しい完了ライドが共存するケースを確認する。SQL 回数だけでなく、新しい SQL の実行時間・走査量と API の平均 / p95、全体スコアを比較する。

初期案の 1 SELECT は DB 内の走査量が増えたため、[初期案](../step5-initial/README.md)から調整した。実環境の EXPLAIN で、最新座標の取得が履歴のソートから索引の skip scan に変わることを確認。追加の索引変更は採用していない。

ベンチマーカーは変更なし。全 SQL 記録・60 秒走行・Colima の資源割当・DB の耐久性設定は固定。旧・新の Docker イメージを切り替えて交互に計測した。各集計は既存 tick の最初から最後までで、SSE の HTTP 時間は接続継続時間。SQL 累積秒は並列実行の合計。

実装差分はこのレポートと同じコミット。各計測時の HEAD は実装前のコミットなので、実際の実行物は保存した image ID でも識別する。[実行情報](./runs.json)。生ログは `_tmp/profiles/` に保存し、正規化した集計のみ Git に含める。

採用: スコア中央値は比較元 117,268 → 164,014（+39.9%）。近隣検索の平均は 448 / 511ms → 52 / 42ms、p95 は 1,059 / 1,296ms → 169 / 139ms。初期案の SQL への集約だけよりも、走査量を抑える構成が有効だった。全 12 テスト PASS。

調整後の候補抽出 SQL の累積時間は 90 / 66 秒で、初期案初回の約 335 秒より小さい（候補 ID の未完了確認は別 SQL）。処理量が増えているため、全 SQL 時間は比較元より大きい。全体の DB 負荷が一様に減ったとは主張しない。[初期案の実行計画](./initial-plan.txt)と[候補抽出の計画](./candidate-plan.txt)を保存した。

警告: 比較元 `20261006-221906` はユーザー名の一意制約違反により登録 500 が 1 件。変更後 `20261006-221647` は椅子アクティベート 401 が 2 件あり、アプリのログでは invalid access token。登録用 DB 接続のログに 13:17:29.215 の BEGIN、その終了処理を挟まず 29.230 / 29.240 の INSERT、次の BEGIN は 29.264 と記録されていた。別接続の認証 SELECT はその間に 0 件を返している。BEGIN 待ちのキャンセルで接続がトランザクションを残したまま再利用される可能性を、別の整合性修正として検証する。2 回目の変更後は警告なしの PASS。警告を除外して中央値を計算していない。
