# #2: 配車イベントと迎車時間による割り当て（不採用）

新規ライド、椅子の稼働開始、椅子への通知済み記録を契機に、プロセス内の単一 worker が配車する。イベントをまとめ、配車処理後に 50ms の間隔を設けて DB の過剰な呼び出しを抑える。500ms の定期再確認と既存 matcher も維持し、イベント取りこぼしを回復する。

待機ライドがない場合は椅子のロックを省略する。距離 / 速度による選択、6 状態の通知完了を待つ条件、同時配車のロック順は維持。初期化中は共通の読み書きロックで worker を待機させる。

HTTP の `/internal/matching` は worker を起こして返すため、その応答時間は配車完了時間ではない。配車待ちの不満率、実際の割り当て数、全体スコアで評価する。SQL の走査量・起動頻度増加も比較する。

除外した実行: `20261006-210155` は負荷走行中にホストの SSH ポート転送と Docker ソケット転送が切断。VM 内の Docker は動作していた。接続拒否による FAIL のため比較に含めず、VM を再起動せずに転送と MySQL の計測前 7 設定を復元して再計測した。

初期案ではスコア低下が再現したため、待機候補全体で迎車時間の短い組を選ぶ貪欲法へ修正した。最も古い依頼が 2 秒以上待っている場合は先に割り当て、近い新規依頼だけが選ばれ続けることを避ける。2 秒は検証用の仮説値で、最適値とは主張しない。11 テストで短距離優先と長期待機の優先、同時配車・椅子の重複利用防止を確認。

ベンチマーカーは変更なし。全 SQL 記録・60 秒走行・Colima の資源割当・DB の耐久性設定は固定。旧・新の Docker イメージを切り替えて交互に計測した。各集計は既存 tick の最初から最後までで、SSE の HTTP 時間は接続継続時間。SQL 累積秒は並列実行の合計。

検証した実装差分は rejected.patch.gz に保存。運用コードには適用していない。各計測時の HEAD は実装前のコミットなので、実際の実行物は保存した image ID でも識別する。[実行情報](./runs.json)。生ログは `_tmp/profiles/` に保存し、正規化した集計のみ Git に含める。

不採用: 比較元 104,148 / 105,602 に対し 93,577 / 94,955。配車待ちの不満は 56.3% / 56.6% → 27.5% / 27.1% に減ったが、迎車時間の不満は 36.5% / 37.0% → 57.2% / 50.2% に増えた。位置更新は増えても評価 API 件数は減り、スコア低下が再現した。実行頻度・割り当ての調整は元に戻し、[検証した差分](./rejected.patch.gz)のみ保存する。[起動のみの初期案](../step2-initial/README.md)も不採用。以降は #1 の実装を比較元とする。
