# #1: 位置更新の保存と状態確認をまとめる

位置更新を最大 1ms / 64 件でまとめ、座標履歴の INSERT と最新 ride / 状態の取得をまとめる。異なる椅子のみ同じバッチに入れ、同じ椅子は受信順に処理する。状態遷移を含めて commit 後に成功応答と通知を返し、履歴の間引きや耐久性設定の変更は行わない。

初回計測後、初期化とキャンセル済みの待機リクエストが競合しないよう、世代番号と DB 初期化ロックによる保護を追加した。最終版の Rust 10 テストは、保存後の応答、PICKUP / ARRIVED の一度だけの生成、並行 32 件、失敗時の rollback、初期化前の待機要求の拒否を含む。

比較元の再計測は前回の 94,797 と異なる値になったため、過去値からの改善率は使わず今回の新旧比較を採用する。応答時間だけでなく処理件数・書き込み回数も比較する。各 run の slp 全件は `slp.csv.gz` に保存。

スコア中央値: 比較元 **61,220** → 変更後 **90,254**（+47.4%）。各構成 2 / 2 回で、ばらつきの評価は限定的。

ベンチマーカーは変更なし。全 SQL 記録・60 秒走行・Colima の資源割当・DB の耐久性設定は固定。旧・新の Docker イメージを切り替えて交互に計測した。各集計は既存 tick の最初から最後までで、SSE の HTTP 時間は接続継続時間。SQL 累積秒は並列実行の合計。

実装差分はこのレポートと同じコミット。各計測時の HEAD は実装前のコミットなので、実際の実行物は保存した image ID でも識別する。[実行情報](./runs.json)。生ログは `_tmp/profiles/` に保存し、正規化した集計のみ Git に含める。

採用: 変更後の両実行でスコアと位置更新件数が比較元を上回った。位置更新の平均は比較元 103 / 95 ms に対し 107 / 102 ms で、応答時間の短縮は確認できていない。今回確認できた効果は処理量の増加と SQL 累積時間の減少。
