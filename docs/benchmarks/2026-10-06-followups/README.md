## 採否の要点

- #2: 配車待ちは減ったが迎車の不満とスコアが悪化したため不採用。初期案と再調整案の両方を記録した。
- #5: N+1 の解消だけでは走査が重かったため、候補の抽出と稼働中判定を分けて再比較した。
- #6: 評価集計回数・時間は減ったが、3 回比較の中央値でスコアが低下。COMMIT の増加を誤差と決めつけず不採用とした。
- #7: スコア差は +1.1% と小さい。採用根拠はオーナー一覧が平均 172 / 193 ms → 15 / 15 ms に短縮し、実データの距離照合も一致したこと。全体スコアの大幅な改善とは扱わない。
- #8: 評価統計の取得は約 35〜42 秒 → 約 1.5〜1.7 秒に短縮したが、スコア改善は未確認。768 台の集計値が正しいことと、性能面で採用する根拠を分けて判断した。

## 整合性と計測基盤

採用済み構成および #8 候補では Rust の 13 テスト（MySQL・実 HTTP を使う統合テストを含む）に成功。位置更新の永続化、状態遷移、初期化前のキューの拒否、決済の冪等性、通知順序・再接続・利用者分離、キャッシュと履歴の整合性を検証した。プロファイル集計の回帰テスト 6 件も成功。ベンチマーカーのソース差分はない。

計測中に見つかった SSE 切断時のトランザクション漏れは、[別の修正と記録](./step5-safe/README.md)（`ed2e762d`）に分けた。修正前に失敗する決定的な再現テストを作り、修正後のベンチ 2 回が警告なしで通ることを確認した。#6 以降は比較元にもこの修正を含めた。

一部の PASS には `users.username` の一意制約違反による CODE=17 がある。登録処理は変更せず、警告を隠したり、その回だけ除外したりせずに各レポートへ記載した。条件違反・転送障害・中断で比較から除外した試行は、該当レポートに理由を残した。

[SSH 転送障害の回避と再現手順](./forwarding/README.md)。#3 以降は比較元と変更後を同じ転送経路で計測した。各ベンチ後に MySQL の計測前 7 設定を復元・照合した。正規化済み alp / slp と計測範囲・イメージ ID は各レポート、生ログはローカルの `_tmp/profiles/` に保存した。

終了時は採用済みの #7 イメージを通常の `development-webapp` として起動し、SQL ディレクトリのマウントも通常構成へ戻した。試験用コンテナと 5 つの試験用 DB、不採用の評価キャッシュ用テーブルを削除し、決済先をローカル決済モックへ戻した。再生成できるフィルタ済み SQL ログだけを削除し、元の SQL ログは保存している。Docker / HTTP / MySQL / 決済モックの接続を確認済み。SSH 転送は上記の復旧手順に記載したバックグラウンドプロセスで継続している。
