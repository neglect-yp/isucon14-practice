# #8: 椅子評価の件数・合計の保持（不採用）

評価の集計は N+1 解消済みだが、通知ペイロードごとに椅子のライドと CARRYING / ARRIVED / COMPLETED の存在を再確認していた。#6 は不採用とし、毎回の集計を件数・評価合計の保存値に置き換える効果を検証する。

初期データは従来と同じ 3 状態の存在条件で集計し、状態履歴が重複してもライドを二重計上しない。評価保存と同じトランザクションで件数と合計を加算する。#4 のライドロックと COMPLETED の確認により、並行要求や再試行で増分を二重適用しない。平均は合計 / 件数で計算し、該当ライドがない場合は 0 を返す。

集計テストでは実際の初期化 SQL を読み込み、従来と同じ対象判定と平均を確認する。並行決済の統合テストで 1 回分だけの加算、SSE テストで他利用者の評価が通知に反映されることを検証する。

MySQL と実 HTTP を使う統合テストを含む 13 件に成功。`20261006-230711` の CODE=17 は `users.username` の一意制約違反（MySQL 1062）であり、この回も比較に含めた。

## 採否と整合性

今回は不採用。評価統計の取得は累積 42.155 / 35.490 秒 → 1.519 / 1.712 秒、位置更新は平均 99 / 97 ms → 85 / 96 ms に短縮した。しかし評価 API 件数は 2,434 / 2,299 → 2,191 / 2,308、平均時間は 344 / 341 ms → 354 / 361 ms となり、スコアの改善は確認できなかった。

SQL 全体は累積 430.122 / 368.660 秒 → 342.091 / 430.961 秒、COMMIT は 123.602 / 113.288 秒 → 125.768 / 189.185 秒。集計 SQL の短縮だけを成功扱いせず、追加書き込み・待ち時間・処理量の変化との因果関係は未確定として残す。2 回目の新旧スコアは近いが、2 回ずつの中央値は -3.1%。キャッシュが常に悪いと断定する結果ではなく、今回の実装を残す根拠が不足したという判断。

最後の負荷後、従来の条件で全ライドを再集計して 768 台の評価件数・評価合計を照合し、不一致 0 件。ライドのない椅子のキャッシュも 0 件だった（[確認 SQL](./verify-stats.sql)）。採用済みの距離集計についても 837 台の総距離・最終更新時刻の不一致は 0 件だった。整合性を確認したうえで、性能面の採否を分けた。
